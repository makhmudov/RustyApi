# CLI `tez`

```sh
cargo install rustyapi-cli
```

| Команда | Что делает |
|---|---|
| `tez new myapp` | проект: `src/{main,lib}.rs`, `routers/`, `models/`, `migrations/`, `tests/`, `.env` со случайным `SECRET_KEY`, `docker-compose.yml` (Postgres) |
| `tez dev` | сборка, запуск, перезапуск при изменениях `*.rs`, `Cargo.toml`, `migrations/*.sql`, `.env*` |
| `tez run` | `cargo build --release` и запуск |
| `tez migrate new <имя>` | `migrations/<время>_<имя>.up.sql` + `.down.sql` |
| `tez migrate run` / `revert` / `status` | применить / откатить последнюю / показать |
| `tez generate crud post` | модель `Post`, роутер `/posts` (5 эндпоинтов), миграция, тест; роутер подключается в `src/lib.rs` |
| `tez routes` | таблица эндпоинтов (`--json` для скриптов) |

## tez dev

Как `uvicorn --reload`, но с учётом компиляции:

- пока идёт `cargo build`, старый сервер продолжает отвечать;
- после успешной сборки старый процесс получает SIGTERM (через 5 с — kill), затем запускается новый;
- при ошибке компиляции cargo печатает её как обычно, а сервер остаётся на прошлой версии до
  следующего изменения;
- изменения собираются 300 мс (сохранение нескольких файлов — одна пересборка); `target/`, `.git/`
  и временные файлы редакторов игнорируются.

Если пересборка дольше 5 секунд, `tez` один раз подскажет, как подключить линкер mold.

Аргументы приложению — после `--`: `tez dev -- --flag`. В workspace с несколькими бинарниками:
`tez dev -p api --bin server`.

## tez routes

Собирает приложение и запускает его с `RUSTYAPI_PRINT=routes`: `App::run()` печатает маршруты и
выходит, не поднимая сервер и не подключаясь к базе. `RUSTYAPI_PRINT=openapi` печатает схему OpenAPI.

## Миграции

`DATABASE_URL` берётся из окружения, `.env` или `--database-url`. Если в каталоге уже есть простые
миграции sqlx (`0001_init.sql` без `.up`/`.down`), `migrate new` создаёт такую же простую. Версия
миграции — время создания, но всегда больше существующих.
